# OPA 在本课题中的技术内容

## 1. 研究问题

本课题关注的不是大模型“说了什么”，而是智能体能否调用文件、数据库、浏览器、系统命令和外部接口执行真实动作。模型输出具有概率性，单靠提示词拒绝无法稳定满足政企场景的最小权限、关键操作审批、过程可审计和责任可追溯要求。因此，本方案在模型与真实工具之间引入独立的策略决策点，采用 Open Policy Agent（OPA）将制度规则写成可测试、可版本化的 Rego 策略。

## 2. 技术路线

系统先把自然语言任务转换为结构化候选动作，字段包括主体身份与角色、任务编号、工具、操作、目标资源、完整参数、风险等级、数据等级、网络区域、执行环境、历史重复次数和审批凭证。OPA 对该 JSON 进行动态判断，输出 `allow`、`require_approval` 或 `deny`。MCP/API 网关根据结果执行放行、暂停或阻断；高风险动作即使被放行，也必须进入 gVisor、Firecracker、Kata 或 Wasmtime 等隔离环境。

## 3. 策略算法

策略采用“不可批准风险优先、审批风险其次、默认最小权限”的顺序：

1. 检查字段完整性、工具可信状态、角色权限、主体密级和资源范围；
2. 对敏感外发、破坏性命令、沙箱缺失、网关绕过、异常重复和非白名单外联直接阻断；
3. 对转账、写入、删除、外发、命令执行、导出、部署、大额、机密数据、非工作时段和大批量处理转入审批；
4. 对审批凭证检查状态、任务绑定、动作摘要、有效期、审批人角色、职责分离和一次性使用；
5. 满足全部约束后允许执行，并输出统一审计记录。

本方案不把“审批通过”理解为永久授权。审批摘要由 `SHA-256(JSON(task_id, action))` 计算，只要工具、资源或参数发生变化，摘要即不一致，策略会以 `D103_APPROVAL_ACTION_TAMPERED` 阻断。这样可以解决审批后改金额、改收件人、改文件路径等常见绕过问题。

## 4. 数据集与实验设计

项目构建了 55 条合成政企测试用例，覆盖合法放行 10 条、需要审批 12 条、有效审批后放行 12 条、硬阻断 13 条、非法审批凭证 8 条。测试对象包括数据库、文件、邮件、支付、Shell、浏览器、API 和插件等工具，重点覆盖越权、密级不足、受保护资源、敏感外发、危险命令、无沙箱执行、绕过网关、异常任务链、外联白名单，以及审批篡改、跨任务、过期、自批、越权和复用。

评测同时观察安全性和可用性：安全性指标包括危险动作阻断率、非法审批凭证阻断率和危险动作误放行数；可用性指标包括合法动作放行率和需审批动作路由准确率；工程指标包括单元测试覆盖率、原因码准确率和策略求值性能。

## 5. 实际结果

实验使用 OPA 1.19.0 完成。严格语法检查通过，31 个 Rego 单元测试全部通过。55 个批量场景的三态决策准确率和原因码准确率均为 100%；危险动作阻断率、合法动作放行率、需审批动作路由准确率和非法审批凭证阻断率均为 100%，危险动作误放行数为 0。核心策略和决策日志脱敏两个生产策略文件覆盖率均为 100%，包含测试代码后的全部 Rego 覆盖率为 99.61%。OPA 原生基准约为 0.35-0.36 毫秒/次。

逐条启动 CLI 的最终测试机端到端平均耗时为 57.9 毫秒、P95 为 63.3 毫秒，该时间包含 Windows 进程启动、策略加载和数据加载，不代表 sidecar 或嵌入式部署的纯策略延迟。因此答辩时应优先引用 OPA 原生 `opa bench` 结果，并把 CLI 数字明确标注为复现实验端到端耗时。

## 6. 先进性与作品提升点

与简单 RBAC 不同，本方案能结合金额、时段、密级、资源、网络区域、任务历史和沙箱状态动态判断；与只返回允许/拒绝的策略不同，本方案输出“允许—审批—拒绝”三态结果；与普通审批流不同，本方案把审批绑定到任务与完整参数，能够检测批准后篡改和跨任务复用；同时输出可机读原因码、必需控制项和审计字段，便于网关阻断、告警和统计。

## 7. 工程边界

OPA 是策略决策点，不是完整审批系统和执行沙箱。审批等待与恢复需要 LangGraph 或 Temporal，审批使用次数需要数据库原子更新，策略结果需要 ToolHive、Envoy 或 API Gateway 强制执行，真实代码和命令需要 gVisor、Firecracker、Kata 或 Wasmtime 隔离。该边界不是缺点，而是符合“策略决策点与策略执行点分离”的纵深防御设计。

## 8. PPT 可直接使用的三页结构

### 第 1 页：OPA 把自然语言任务变成可执行的三态安全决策

- 输入：用户/服务账号、任务、工具、资源、参数、风险与数据等级；
- 规则：最小权限、动态条件、关键操作审批、不可批准风险；
- 输出：allow / require_approval / deny；
- 结论：OPA 负责判断，网关负责强制执行。

### 第 2 页：审批凭证绑定任务和完整参数，防止批准后被替换

- 动作摘要：SHA-256(task_id + 完整 action)；
- 校验：有效期、审批角色、发起人与审批人分离、一次性使用；
- 阻断：改金额、改资源、跨任务、过期、自批、复用；
- 输出：稳定原因码，便于审计与答辩解释。

### 第 3 页：55 个用例和 31 个单元测试验证可行性

- 55 个政企工具调用场景，三态决策与原因码全部正确；
- 危险动作阻断率、合法动作放行率、审批路由准确率均为 100%；
- 核心策略覆盖率 100%，OPA 原生求值约 0.35 ms/次；
- 结论：开源组件可复现，具备接入 MCP/API 网关的工程基础。

## 9. 下一阶段已实现：LangGraph 持久化审批

在 OPA 三态策略之后，本项目进一步接入开源 LangGraph 1.2.10 和 SQLite 检查点。OPA 返回 `require_approval` 时，工作流调用 `interrupt()` 将任务暂停，并以唯一 `thread_id` 保存当前状态；审批人通过同一任务恢复时，系统签发绑定任务编号与完整动作摘要的一次性凭证，然后再次请求 OPA。只有第二次 OPA 返回 `allow`，模拟工具节点才会生成执行回执。因此，人工审批并不是直接绕过策略，而是给策略补充一条可验证的授权证据。

实际测试共 10 项，全部通过：低风险动作直接放行；高风险动作准确暂停；批准后恢复并仅执行一次；拒绝后不执行；修改参数会清空旧凭证并重新审批；审批后金额被修改时返回 `D103_APPROVAL_ACTION_TAMPERED`；发起人自批和无角色审批均被阻断；凭证换到其他任务时返回 `D102_APPROVAL_TASK_MISMATCH`；关闭并重新创建工作流后，可以依靠 SQLite 从原暂停点恢复。测试中的工具执行均为 `simulated_only`，不会触发真实转账或系统操作。

开源工具地址：

- LangGraph：https://github.com/langchain-ai/langgraph —— 构建有状态智能体工作流，`interrupt()` 用于人工介入；
- LangGraph SQLite Checkpoint：https://pypi.org/project/langgraph-checkpoint-sqlite/ —— 把任务检查点持久化到 SQLite；
- OPA：https://github.com/open-policy-agent/opa —— 对恢复后的动作和审批凭证再次进行策略校验。

对应数据与证据：`datasets/approval_workflow_cases.jsonl` 包含 9 类工作流安全场景；`reports/approval/approval_unit_tests.txt` 是测试原始输出；`reports/approval/approval_evaluation_report.md` 是量化结论；四个 `reports/approval/approval_demo_*.json` 保存每条演示路径的实际决策和执行回执。

## 10. 强制阻断层：一次性执行票据与 fail-closed

为了避免 Agent 忽略 OPA 的 `deny`，本项目实现了独立强制执行网关。OPA 不可用、返回未知结果、要求审批或直接拒绝时，网关都不会产生执行票据。只有 `allow` 才签发有效期 30 秒的 HMAC 票据，票据同时绑定 `task_id` 和完整 action 摘要。工具适配器必须在 SQLite 事务中原子核销，第二次或并发重复使用会返回 `G206_TICKET_REPLAY`。授权后修改参数返回 `G205_TICKET_BINDING_MISMATCH`；无票据直连、签名篡改、过期和未注册适配器也均被拒绝。

测试覆盖了 16 路并发核销，同一票据只有 1 次成功、其余 15 次全部按重放阻断。审计日志不保存票据明文，并递归隐藏密码、API Key、访问令牌和 Authorization 等敏感字段。生产侧可使用 OPA-Envoy 的 External Authorization 过滤器做网络层前置阻断，且必须配置 `failure_mode_allow: false`；后端仍需完成票据签名和原子核销。

## 11. 安全内核：Wasmtime 最小能力执行

项目使用 Wasmtime 47.0.1 验证高风险工具的隔离执行。沙箱默认不注入 WASI 和任何主机函数，因此 WebAssembly 模块不能直接访问文件系统、网络、环境变量或宿主进程。每次运行限制 2 MiB 内存和固定燃料预算，只允许调用注册模块的 `run` 入口。无限循环因燃料耗尽返回 `K006_CPU_BUDGET_EXCEEDED`；请求 `wasi_snapshot_preview1.fd_write` 被 `K002_HOST_IMPORT_FORBIDDEN` 拒绝；512 页初始内存和非白名单导出入口也不能实例化执行。

最终在 Windows 测试机上跑通 `OpenClaw/MCP → AgentGuard → OPA → LangGraph 暂停审批 → OPA 复核 → OpenBao外部签名/三节点Raft HA → 强制网关 → 共享票据与审批核销 → Wasmtime/QEMU隔离`。OPA单元测试31/31、策略数据集55/55、Python安全与接入测试174/174、OpenClaw最小接入9/9、固定模型 synthetic fixture 5/5、CLI模型回合14/14、Control UI模型回合16/16、网络5/5、Keycloak7/7、OpenBao10/10、Raft HA 8/8、QEMU11/11、综合检查23/23全部通过，危险场景误执行次数为0。OpenClaw模型证据仅覆盖当前隔离回环配置、回环静态开发身份和合成公告，不是公开基准成绩或生产验收。

需要明确的是：Keycloak、OpenBao外部签名/共享核销、真实本地测试业务和QEMU独立来宾内核均已有实测；OPA-Envoy、ToolHive、Kata和Firecracker产品E2E仍受容器/KVM环境限制。真实业务API和真实日志的安全接入流水线已完成，但没有单位授权的凭据与数据，不能冒充生产E2E。
