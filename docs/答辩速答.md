# OPA 部分答辩速答

## 为什么选 OPA？

OPA 是通用策略引擎，输入和输出都是结构化数据，适合把主体、工具、资源、参数、金额、密级、时段和审批状态放在同一套规则中判断。Rego 策略可以版本管理、单元测试和独立部署，不需要把安全规则散落在每个业务工具里。

## OPA 是不是安全内核？

不是。OPA 是策略决策点，负责回答“允许、审批还是拒绝”。真正限制文件、网络、进程和系统调用的是 gVisor、Firecracker、Kata 或 Wasmtime。两者分别解决“该不该做”和“即使误放行，最多能造成多大损害”。

## 为什么不只返回允许或拒绝？

政企系统有大量合法但高风险的动作，例如付款、外发、删除和部署。全部拒绝会导致系统不可用，直接允许又不安全，所以需要第三种 `require_approval` 状态，让任务暂停并由有权人员确认。

## 审批通过后，Agent 改金额怎么办？

审批凭证绑定任务编号和完整动作的 SHA-256 摘要。执行前 OPA 重新计算摘要，只要金额、收件人、文件路径、命令或目标资源发生变化，就返回 `D103_APPROVAL_ACTION_TAMPERED` 并阻断。

## 同一个审批能不能重复使用？

不能。策略要求 `max_uses=1` 且 `use_count=0`。真实系统中由审批服务或数据库原子更新使用次数，OPA 在每次执行前检查。仅靠 OPA 内存不能可靠维护跨实例状态。

## 如何防止用户自己审批自己？

策略比较发起人和审批人标识，二者相同就返回 `D105_SELF_APPROVAL`。同时审批人必须拥有 `business_approver` 或 `security_approver` 角色，实现职责分离。

## OPA 返回 deny 后，Agent 不理它怎么办？

所以策略不能只放在 Agent 框架内部。本方案要求所有真实工具调用经过 MCP/API 网关，由网关根据 OPA 结果强制放行、暂停或阻断，并关闭后端直连端口，避免旁路。

## 你们怎么测试？

一层是 31 个 Rego 单元测试，验证具体规则和日志脱敏；另一层是 55 个 JSONL 批量场景，验证 allow、require_approval、deny 三态输出和原因码；同时生成覆盖率、逐例结果、混淆矩阵和性能基准。

## 100% 准确率是否说明绝对安全？

不是。100% 只说明当前 55 个已定义场景全部符合预期。数据是合成的小规模验证集，后续还要加入真实制度、更多工具、并发状态、编码混淆、跨步骤组合和生产日志回放，不能把实验集结果等同于生产安全承诺。

## OPA 的性能如何？

本机 `opa bench` 的纯策略求值约 0.35-0.36 毫秒/次。逐条启动 CLI 的最终测试机端到端平均为 57.9 毫秒，主要是进程和文件加载开销。工程部署应使用常驻 sidecar、Go SDK 或 Wasm，不应为每个请求启动一次 CLI。

## 最小可行组合是什么？

身份由 Keycloak 提供，OPA 负责规则和三态决策，网关负责强制阻断，审批服务保存状态并生成一次性凭证，高风险工具进入 gVisor 等沙箱，AgentDojo/自建数据集负责回归测试。当前原型已经完成 OPA 策略、LangGraph 持久化审批、样例、测试和安全模拟执行部分。

## 第二阶段审批层可能追问

**问：为什么 OPA 后面还要 LangGraph？**

答：OPA 只计算允许、审批或拒绝，不负责把一个运行中的任务暂停几分钟后再恢复。LangGraph 保存工作流状态和暂停点，OPA 仍然掌握最终放行权，两者分工不同。

**问：批准后为什么还要再查一次 OPA？**

答：审批期间参数、资源或任务都可能被替换。恢复后再次校验，可以验证审批凭证绑定的 `task_id` 和动作摘要是否仍与当前请求一致，防止“批的是 5000 元、执行时变成 50 万元”。

**问：程序关掉后暂停任务会不会丢？**

答：不会。本原型用 SQLite 保存 LangGraph 检查点，并实际测试了关闭旧连接、重新创建工作流后使用同一 `thread_id` 恢复，测试已经通过。

**问：现在会真的转账吗？**

答：不会。为了安全，执行节点只生成 `simulated_only` 回执。原型验证的是权限、审批和阻断逻辑；接入真实工具必须再经过统一网关和沙箱。

**问：你怎么证明审批不是摆设？**

答：有四条 JSON 演示证据和 10 个自动化测试。批准后只有一次模拟执行；拒绝、参数篡改、自批、无角色审批和跨任务复用的执行回执都为 0。

## 强制阻断与安全内核可能追问

**问：Agent 如果不执行 OPA 的 deny 怎么办？**

答：Agent 没有真实工具的直连权。统一网关只在 OPA 返回 `allow` 时签发短时执行票据，工具后端必须核销票据；没有票据即使直接调用后端也返回 `G201_TICKET_MISSING`。

**问：拿到一张合法票据能不能连续执行？**

答：不能。票据在 SQLite 事务中原子核销，测试用同一票据发起 16 路并发请求，只有 1 次成功，另外 15 次全部返回 `G206_TICKET_REPLAY`。

**问：OPA 宕机会不会默认放行？**

答：不会。网关采用 fail-closed，OPA 异常返回 `G001_OPA_UNAVAILABLE_FAIL_CLOSED` 和 503，不产生票据。OPA-Envoy 生产配置同样要求 `failure_mode_allow: false`。

**问：安全内核具体做了什么？**

答：本机使用 Wasmtime 运行 WebAssembly 工具适配器，不启用 WASI 和主机导入，限制 2 MiB 内存和燃料预算。无限循环、文件写入能力请求、超量内存和错误入口均被实际测试阻断。

**问：为什么没有直接说已经用了 gVisor 或 Firecracker？**

答：测试机是 Windows，没有 Docker 和可用 Linux 发行版，不能诚实地声称完成了 Linux 内核级容器隔离。我们已经实际验证跨平台 Wasmtime，并提供 OPA-Envoy/ToolHive 接入位置；gVisor、Kata、Firecracker 要在 Linux 测试机继续做。

**问：现在整条链路是否跑通？**

答：已经跑通 OPA 决策、LangGraph 持久化审批、OPA 复核、网关签票、OpenBao Transit外部签名、共享CAS核销、Wasmtime与QEMU隔离。最新测试是 OPA 31/31、策略场景55/55、Python安全测试46/46、网络5/5、Keycloak5/5、OpenBao7/7、QEMU9/9、综合检查17/17，危险场景误执行为0。

**问：目前最大的缺漏是什么？**

答：三项高优先级缺漏：真实 Keycloak/OIDC 身份源未接入；OPA-Envoy 和 ToolHive 因无 Docker/Linux 尚未端到端运行；真实业务工具仍是安全模拟。汇报时应称为“可运行原型和生产参考配置”，不能称为生产系统。
